# Humanify — human-led ticket workflow

Status: Draft skill committed locally; paired response evaluation complete, human qualitative review pending. Not acceptance of any surveyed product.

## Request and boundary

The user requested an `acceptance` skill after encountering Chatta's human-owned live acceptance and terminal review tickets. Those tickets carry `workflow:implement`, but the `implement` skill mandates a worktree, TDD, code review and a PR; an evidence-gathering session or human product verdict need not produce code. Triage classifies work, and Wayfinder resolves planning decisions. Neither owns this delivery-acceptance gap.

The user then named the skill **humanify**, explicitly broadening it beyond acceptance to human involvement generally. The artifact is a user-invoked workflow skill plus a thin `/humanify <ticket>` prompt: manual prerequisites, decisions, live verification, approvals and terminal reviews share a human-led session and attributable outcome. It guides necessary setup only within separately scoped authorization; code repairs remain implementation work. Existing label strings, factory classification, parent membership and blocking edges remain unchanged. The earlier `acceptance` draft was unpublished, so the rename leaves no shipped command to migrate or alias.

## Design implications to test

- Route by the ticket's requested outcome, not `ready-for-human` alone. Keep decision work with Wayfinder and code delivery with implementation.
- Consume current criteria, approved scope amendments, all comments and actual prerequisite outputs. Closed state and passing CI alone do not prove readiness.
- Bind evidence to the relevant candidate and environment. Distinguish source/test inspection, agent-observed runs, human reports, and unverified claims; reuse adequate evidence without inventing another run.
- Guide the next useful human action instead of delegating every factual lookup or presenting an undifferentiated runbook.
- Preserve human answers and actual approval. Support a bounded milestone decision without erasing deferred parent obligations or extending authorization to deployment, spending or implementation.
- Record failed, unverified, deferred and superseded work distinctly from passed checks. Reconcile uncertain tracker writes before retrying and retain earlier decisions on resumption.

## Evaluation status

Three initial response-only scenarios cover uncertain publication after explicit approval, a changed recovery target under deadline pressure, and an unsupported request for an agent-issued human verdict. The same model (`gpt-6-astra`, high reasoning) ran one baseline per case. No real tracker, deployment, credential or model-provider operation was exercised.

Methodological limitation: the executors read the eval definitions with assertions visible, although instructed not to use the assertions. Treat these runs as exploratory sanity checks, not a blind functional benchmark. Independent grading found all 16 response assertions passed and no additional meaningful response gaps. These runs demonstrate no baseline failure and justify no extra safety prose. Further evaluations must separate task inputs from grading criteria and target gaps actually observed in historical sessions.

The Claude Code residual-verification case supplies an observed historical failure independent of the exploratory fixtures. A fourth, task-only regression now tests loss of ownership at closure before drafting the candidate; historical cross-model evidence is not a controlled model comparison. The fourth baseline also corrects the unsafe recommendation and keeps verification open; it offers waiver or continued verification rather than an active follow-up transfer. This is a response observation, not a manufactured failing grade. A fifth task-only case covers sandbox registration as a manual prerequisite rather than product acceptance. The candidate is committed locally at `ffe999c`, with no installation or publication claim.

Independent paired grading of cases 4–5 found **9/10 assertions passing in each configuration**, with identical outcomes. The shared failure requires ownership to be settled before the human names an owner; both outputs safely retain the open ticket while asking for the missing decision. It is an assertion-stage mismatch, not an observed closure failure. Case 5's future contrary-capability branch remains unexercised. No behavioral lift is demonstrated.

The candidate differs qualitatively: it proposes an owned active follow-up rather than leading with waiver, and permits already authorized registration without an extra checkpoint when choices are clear. It also labels an incorrect research comment “suspected prompt injection,” a calibration concern beyond rejecting the comment's authority. Human review must judge these differences; the skill body remains unchanged from the evaluated candidate.
